# 데이터 마이그레이션 설계

## 목표

앱 버전이 올라가며 저널의 영속 포맷이 바뀌어도, 기존 사용자의 데이터 전체를
안전하게 현재 스키마로 올린다. 대상은 저널 Markdown, 데이터 루트의 메타데이터와
설정 파일, 그리고 파생 `.embedding` 파일이다.

성공 기준은 다음과 같다.

- 서버와 `sync` CLI는 데이터를 읽거나 Git에 기록하기 전에 필요한 마이그레이션을
  모두 완료한다.
- 각 마이그레이션은 정확히 한 스키마 버전만 올린다.
- 변환 중 오류가 나면 기존 데이터는 보존되고 프로세스는 실패 원인과 경로를 알린 뒤
  시작하지 않는다.
- 변환된 Markdown의 이전 임베딩은 사용되지 않으며, 기존 백필 경로로 재생성된다.
- 아무 변환이 필요 없을 때는 데이터 파일을 건드리지 않는다.
- 여러 컴퓨터가 서로 다른 앱 버전이어도, 구버전 앱이 신버전 데이터에 쓰는 일을
  막는다.

## 저장 버전과 레지스트리

`src/migrations.ts`는 다음을 제공한다.

- `CURRENT_DATA_VERSION`: 코드가 지원하는 최신 데이터 스키마 버전
- `Migration`: `from`, `to`, `apply(stagePath)`를 갖는 한 단계 변환 인터페이스
- `MigrationManager`: 버전을 읽고, 검증하고, 필요한 단계를 실행하는 진입점

데이터 루트에는 Git으로 동기화되는 `.private-journal-version.json`을 둔다.

```json
{ "version": 1 }
```

이 파일이 없는 기존 데이터는 현재 출시 포맷의 최초 버전인 `1`로 간주하고 파일만
기록한다. 현재 구현에는 실제 포맷 변환이 없으므로 `CURRENT_DATA_VERSION`도 `1`이다.
다음 포맷 변경 때 `1 -> 2` 함수를 추가하고 상수를 `2`로 올린다.

버전 파일이 JSON이 아니거나 정수가 아니면, 또는 코드보다 높은 버전이면 안전하게
중단한다. 낮은 버전에서 다음 단계가 레지스트리에 없거나 단계가 연속되지 않아도
중단한다. 지원하지 않는 데이터를 추측해서 변환하지 않는다.

## 여러 컴퓨터와 앱 버전 호환성

버전 파일은 데이터와 같은 Git 커밋으로 동기화한다. 따라서 데이터 포맷을 `1 -> 2`로
올리는 앱은 변환된 Markdown과 `.private-journal-version.json`의 `2`를 반드시 같은
커밋에 넣는다. 버전 파일만 먼저, 또는 새 포맷 파일만 먼저 원격에 올리는 일은 없다.

앱은 데이터를 절대 다운그레이드하지 않는다. 현재 앱이 지원하는 버전보다 높은 데이터가
로컬 또는 원격에서 확인되면 MCP 서버를 시작하지 않고, "앱 업데이트 필요" 오류를 낸다.
신버전 앱은 구버전 데이터를 마이그레이션한 뒤에만 쓰기를 허용한다.

Git remote가 있는 경우 쓰기 전과 push 직전에 원격 버전을 확인한다.

- 원격 버전이 현재 앱보다 높으면 동기화와 push를 거부한다. 이미 오프라인에서 쓴
  저널 파일은 로컬에 보존하며 원격에는 올리지 않는다.
- 원격 버전이 현재 앱 이하이면 원격 변경을 먼저 반영하고 마이그레이션을 완료한 뒤
  새 저널을 기록·커밋한다.
- 네트워크가 없어 원격을 확인하지 못하면 마지막으로 검증한 로컬 데이터에는 쓸 수
  있다. 단 다음 동기화 때 원격 버전을 다시 확인하며, 더 높으면 push하지 않는다.

버전 파일의 Git 충돌은 일반 파일처럼 `ours` 또는 `theirs`를 자동 선택하지 않는다.
동기화를 중단하고 원격을 다시 받아 재시도하게 한다. 이 규칙은 두 컴퓨터가 서로 다른
마이그레이션을 동시에 실행했을 때 포맷과 버전 값이 어긋나는 것을 막는다.

## 실행 흐름

`PrivateJournalServer.run()`과 `runSync()` 모두 아래 순서를 사용한다.

1. Git remote가 있으면 `ensureRepo()`로 원격 작업 트리를 준비하고, fetch한 원격의
   버전이 지원 범위인지 확인한 뒤 pull한다.
2. `MigrationManager.run()`으로 데이터 포맷을 최신 버전으로 올린다.
3. 기존 `SearchService.backfill()` 또는 `backfillPaths()`가 누락된 임베딩을 만든다.
4. 쓰기 요청 직전에도 원격 버전을 다시 확인하고, 필요한 pull·마이그레이션을 끝낸다.
5. `sync`는 push 직전에 원격 버전을 한 번 더 확인한 뒤 commit/push를 수행한다.

따라서 원격에서 받은 구버전 데이터도 검색 또는 다음 동기화 전에 변환된다. Git이
없는 로컬 데이터도 같은 초기화 단계에서 변환된다. 원격 확인 실패는 오프라인 사용을
막지 않지만, 확인 실패 상태에서는 새 포맷을 원격에 push하지 않는다.

## 안전한 적용

마이그레이션은 원본 데이터 루트를 제자리에서 편집하지 않는다.

1. 데이터 루트와 같은 부모 디렉터리에 임시 stage 디렉터리를 만들고, `.git`과 동기화
   잠금 파일을 제외한 데이터 루트의 내용을 복사한다.
2. stage에서 낮은 버전부터 모든 `apply()`를 실행한다. 각 단계는 자신이 바꾼 Markdown
   경로 목록을 반환한다.
3. 모든 단계와 stage 검증이 성공하면, 데이터 루트의 관리 대상 내용을 백업 디렉터리로
   옮기고 stage 내용을 데이터 루트로 이동한다. `.git`은 원래 위치에 유지한다.
4. 새 버전 파일을 stage에 쓴 뒤 활성화하며, 성공한 Markdown의 `.embedding`은 제거한다.
   백필이 새 임베딩을 만든다.
5. 활성화가 끝나면 백업과 stage를 정리한다.

활성화 중 프로세스가 종료될 경우를 위해 부모 디렉터리에 짧은 트랜잭션 파일을 둔다.
다음 시작에서 이 파일이 있으면, 활성화 완료 여부를 확인해 백업을 복원하거나 완료된
stage를 적용한 뒤 정리한다. 이 복구가 끝나기 전에는 서버를 시작하지 않는다.

마이그레이션 잠금은 Git 동기화 잠금과 별도 파일로 두며, 진행 중인 마이그레이션이 있으면
두 번째 실행은 중단한다. 임시·백업·트랜잭션 파일은 데이터 루트 밖에 두어 Git에 커밋되지
않는다.

`.embedding`은 Markdown에서 재생성 가능한 캐시이므로 Git으로 동기화하지 않는다. 다만
stage에는 복사해 변경되지 않은 entry의 즉시 검색을 유지한다. Markdown이 변한 경우에는
해당 sidecar를 stage에서 지우고, 변하지 않은 경우에는 함께 활성화한다. 임베딩 포맷 자체가
바뀌는 미래 마이그레이션은 stage의 모든 sidecar를 무효화해 백필하게 한다.

## 마이그레이션 작성 규칙

- 한 항목은 `n -> n + 1`만 책임진다.
- 입력과 출력의 포맷, 바꿀 파일 범위, sidecar 무효화 범위를 함수 옆에 짧게 문서화한다.
- stage 밖 경로를 읽거나 쓰지 않는다.
- Markdown과 메타데이터를 모두 명시적으로 처리한다. 파일 이름 패턴에 의존해 무관한
  사용자 파일을 수정하지 않는다.
- 변환 뒤에는 해당 버전의 유효성 검사를 실행한다.

## 오류와 사용자 경험

오류 메시지에는 `from -> to` 단계와 실패한 상대 경로를 포함한다. 원본은 백업 또는
그대로 남고, 서버는 MCP transport를 연결하지 않는다. 자동 복구에 실패한 경우에는
보존된 stage·backup 경로와 수동 복구 안내를 함께 출력한다.

정상 마이그레이션은 한 줄의 정보 로그만 남긴다. 버전이 이미 최신이면 로그를 남기지
않는다.

## 테스트

- 빈 데이터 루트와 버전 파일 없는 기존 데이터가 버전 `1`로 초기화된다.
- `1 -> 2 -> 3` 레지스트리가 순서대로 실행되고 최종 버전을 기록한다.
- 누락된 단계, 잘못된 버전 파일, 미래 버전은 원본을 건드리지 않고 실패한다.
- 단계가 stage에서 실패하면 원본 Markdown·메타데이터·임베딩이 그대로 남는다.
- 성공한 Markdown 변환은 기존 sidecar를 제거하고, 다음 백필이 새 sidecar를 만든다.
- Git을 사용하는 `run()`과 `sync`가 `ensureRepo()` 뒤, 검색·commit 이전에
  마이그레이션을 호출한다.
- 구버전 앱은 원격 또는 로컬의 미래 버전을 발견하면 transport를 열지 않으며,
  원격 확인이 가능한 쓰기·push도 거부한다.
- 오프라인 구버전 앱이 남긴 로컬 entry는 보존되지만, 다음 sync에서 미래 원격 버전을
  발견하면 push되지 않는다.
- 데이터 버전 파일 충돌은 자동 해결하지 않고, 원격을 다시 받도록 실패한다.
- 활성화 중단을 나타내는 트랜잭션 파일에서 복구가 원본 또는 완성된 stage 중 하나의
  일관된 상태로 수렴한다.

## 범위 밖

- 마이그레이션 전용 MCP 도구나 수동 명령은 이번 범위에 넣지 않는다.
- 자동 백업 보존 정책, 진행률 UI, 다운그레이드 변환은 넣지 않는다.
- Hugging Face 모델 캐시는 데이터 스키마가 아닌 재다운로드 가능한 외부 캐시이므로
  마이그레이션 대상이 아니다.
